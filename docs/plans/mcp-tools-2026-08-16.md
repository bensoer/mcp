# MCP Tools Implementation Plan

## Summary

Add 4 MCP **tools** (distinct from resources) to the server:

| Tool | Input | Output |
|------|-------|--------|
| `discover_standards` | (none) | List of `{uri, name, description}` for all `standards://` resources |
| `discover_workflows` | (none) | List of `{uri, name, description}` for all `workflows://` resources |
| `search_standards` | `{query: string}` | List of matching standards (metadata only) |
| `search_workflows` | `{query: string}` | List of matching workflows (metadata only) |

**Search behavior:** case-insensitive partial match against URI, Name, Description **and** the body of each asset document. Tools return frontmatter metadata only — the agent must then call `resources/read` for full content.

## Goals

1. **Framework-correct** — Use the MCP SDK's actual `AddTool` API with typed handlers (`ToolHandlerFor[In, Out]`), not `AddResource`.
2. **Generic registration** — `BootstrapServer` does not hardcode any tool; it loops over a single slice in `tools/registry.go`. Adding a tool never requires editing `server.go`.
3. **Reusable scaffolding** — One shared helper for "walk assets → parse frontmatter"; tools are thin wrappers around it.
4. **Testable end-to-end** — Follow the existing `internal/server_test.go` pattern (`mcp.NewInMemoryTransports` + in-process `mcp.ClientSession.CallTool`).
5. **Discoverable pattern for future tools** — Document via a skill + rule file.

## Non-Goals

- Runtime plugin / `.so` loading (Go can't do this cross-platform).
- Code-generated registries (over-engineered for 4 tools; explicit is fine).
- Pagination of search results (the corpus is small; revisit if it grows).

## Architecture

### Existing patterns to reuse (do not reinvent)

- `internal/utils/assets.go` — `AssetsFinder` interface already walks `assets/`. Reuse; do not duplicate.
- `internal/server.go` — BootstrapServer currently parses frontmatter per asset and registers with `server.AddResource`. **Extract the frontmatter-parsing loop into a helper** that both resources and tools can use.
- `internal/server_test.go` — `TestBootstrapServer_Integration` shows the exact pattern to follow for tool tests: `NewInMemoryTransports` + `mcp.NewClient` + `cs.Resources(...)` + `cs.ReadResource(...)`. We add `cs.CallTool(...)` to that pattern.

### New package: `internal/tools/`

```
internal/tools/
  types.go         # shared types: ResourceMetadata (used by all tools)
  helper.go        # ListAllMetadata() + SearchMetadata() — walks assets, parses, filters
  discover_standards.go
  discover_workflows.go
  search_standards.go
  search_workflows.go
  registry.go      # RegisterAll slice — single source of tool list
```

Each tool file is **self-contained**: name, description, Input/Output types, a pure handler function, **and** a `Register<Name>Bootstrap` function that wires it into the server. `BootstrapServer` only loops over a single slice — no per-tool hardcoding.

Each tool file exports:
1. `Name` constant — the tool's identifier (`"discover_standards"`)
2. `Description` constant — human-readable description (used by LLM clients to pick the right tool)
3. `Input` struct (typed, validated by SDK against JSON Schema)
4. `Output` struct (typed, marshaled automatically into `CallToolResult.StructuredContent`)
5. A **pure handler function** with signature `func(ctx, *mcp.CallToolRequest, Input, utils.AssetsFinder) (*mcp.CallToolResult, Output, error)` — dependencies (the finder) are passed explicitly
6. A `Register<Name>Bootstrap(server *mcp.Server, finder utils.AssetsFinder)` function that closes over the finder and calls `mcp.AddTool`

Tool files have **names** (`discover_standards`), not URIs. `tools://` URIs were a mistake in earlier drafts and are removed.

### Why a per-tool `Register<Name>Bootstrap` function (and not just method values)

`mcp.AddTool` is generic with `[In, Out any]`. Each tool has a different `In/Out` pair, so their handlers have different concrete types and **can't share a single `[]ToolHandlerFor[…, …]` slice**. The cleanest Go solution is for each tool file to expose its own non-generic `Register<Name>Bootstrap` function that calls the generic `mcp.AddTool` internally. `RegisterAll` is a `[]func(*mcp.Server, utils.AssetsFinder)` — a single concrete type that accepts any number of tools.

### Why pure free functions (and not methods on a `Searcher` struct)

The SDK's `ToolHandlerFor[In, Out]` signature only passes `(ctx, req, input)`. If the handler is a method on `*Searcher`, the dependency (the finder) leaks into every tool file as a struct they must understand. **Cleaner:** the handler is a pure free function that takes the finder as an explicit parameter. `Register<Name>Bootstrap` closes over the finder with a one-line lambda, so the dependency stays invisible inside the tool's implementation.

### Naming convention (helper vs. registrar)

For each tool there are **two** functions in the file:

| Function | Visibility | Role |
|---|---|---|
| `<name>` (e.g. `discoverStandards`) | **unexported** (lowercase) | Internal helper that does the actual work — never registered as a tool itself |
| `Register<Name>Bootstrap` (e.g. `RegisterDiscoverStandardsBootstrap`) | exported | Wires the helper into the MCP server via a closure. The closure captures the finder and is what actually gets registered as the tool |

The tool that the LLM calls is **the closure**, not the helper. The helper is just an internal building block — keeping it unexported signals that nothing outside the `tools` package should be calling it directly. The exported `Name` constant (`"discover_standards"`) is what the MCP client uses to identify the tool.

### Tool registration — single slice

`internal/tools/registry.go` exposes the canonical tool list:

```go
package tools

import (
    "github.com/modelcontextprotocol/go-sdk/mcp"
    "mcp/internal/utils"
)

// RegisterAll is the canonical list of tools. Adding a new tool:
//   1. Create the tool file with Name, Description, types, handler, and Register<Name>Bootstrap
//   2. Append Register<Name>Bootstrap to this slice
var RegisterAll = []func(*mcp.Server, utils.AssetsFinder){
    RegisterDiscoverStandardsBootstrap,
    RegisterDiscoverWorkflowsBootstrap,
    RegisterSearchStandardsBootstrap,
    RegisterSearchWorkflowsBootstrap,
}
```

`BootstrapServer` becomes a single generic loop:

```go
for _, register := range tools.RegisterAll {
    register(server, finder)
}
```

No `Searcher` struct, no constructor — the `AssetsFinder` flows straight from `BootstrapServer` through `RegisterAll` into each tool's closure. Adding a tool = one new entry in `RegisterAll` plus a new file — `BootstrapServer` never changes.

## Tool contracts (MCP-typed)

Each tool lives in its own file. Below is the full layout for `discover_standards.go`; the other three tools follow the same shape.

### `internal/tools/discover_standards.go`

```go
package tools

import (
    "context"

    "github.com/modelcontextprotocol/go-sdk/mcp"
    "mcp/internal/utils"
)

const (
    DiscoverStandardsName        = "discover_standards"
    DiscoverStandardsDescription = "Returns all standards:// resources as {uri, name, description} metadata. Use resources/read on a specific URI to fetch the full document."
)

type DiscoverStandardsInput struct{} // empty — no parameters

type DiscoverStandardsOutput struct {
    Resources []ResourceMetadata `json:"resources"`
}

// discoverStandards is an unexported helper that does the actual work. It is
// NOT the tool itself — the closure passed to mcp.AddTool below is. Keeping
// the helper unexported signals that nothing outside this package should
// call it directly.
func discoverStandards(
    ctx context.Context,
    _ *mcp.CallToolRequest,
    _ DiscoverStandardsInput,
    finder utils.AssetsFinder,
) (*mcp.CallToolResult, DiscoverStandardsOutput, error) {
    all, err := ListAllMetadata(finder)
    if err != nil {
        return nil, DiscoverStandardsOutput{}, err
    }
    return nil, DiscoverStandardsOutput{
        Resources: filterByPrefix(all, "standards://"),
    }, nil
}

// RegisterDiscoverStandardsBootstrap wires the helper into the server. The
// closure captures `finder` and is what actually gets registered as the tool.
// The "Bootstrap" suffix makes the intent explicit: this function bootstraps
// the tool into the server.
func RegisterDiscoverStandardsBootstrap(server *mcp.Server, finder utils.AssetsFinder) {
    mcp.AddTool(server, &mcp.Tool{
        Name:        DiscoverStandardsName,
        Description: DiscoverStandardsDescription,
    }, func(ctx context.Context, req *mcp.CallToolRequest, in DiscoverStandardsInput) (*mcp.CallToolResult, DiscoverStandardsOutput, error) {
        return discoverStandards(ctx, req, in, finder)
    })
}
```

### `internal/tools/discover_workflows.go`

Identical shape; constant is `DiscoverWorkflowsName`, helper `discoverWorkflows`, registrar `RegisterDiscoverWorkflowsBootstrap`.

### `internal/tools/search_standards.go` and `search_workflows.go`

```go
const (
    SearchStandardsName        = "search_standards"
    SearchStandardsDescription = "Searches standards (frontmatter + body) for case-insensitive partial matches of `query`. Returns metadata only ({uri, name, description}). Call resources/read on a matching URI to fetch the full document. The response itself does NOT contain document content."
)

type SearchStandardsInput struct {
    Query string `json:"query" jsonschema:"description=Case-insensitive partial match against URI, name, description, and body. Required."`
}

type SearchStandardsOutput struct {
    Query     string             `json:"query"`
    Resources []ResourceMetadata `json:"resources"`
    Total     int                `json:"total"`
}

func searchStandards(
    ctx context.Context,
    _ *mcp.CallToolRequest,
    in SearchStandardsInput,
    finder utils.AssetsFinder,
) (*mcp.CallToolResult, SearchStandardsOutput, error) {
    matches, err := SearchMetadata(finder, in.Query, "standards://")
    if err != nil {
        return nil, SearchStandardsOutput{}, err
    }
    return nil, SearchStandardsOutput{
        Query:     in.Query,
        Resources: matches,
        Total:     len(matches),
    }, nil
}

func RegisterSearchStandardsBootstrap(server *mcp.Server, finder utils.AssetsFinder) {
    mcp.AddTool(server, &mcp.Tool{
        Name:        SearchStandardsName,
        Description: SearchStandardsDescription,
    }, func(ctx context.Context, req *mcp.CallToolRequest, in SearchStandardsInput) (*mcp.CallToolResult, SearchStandardsOutput, error) {
        return searchStandards(ctx, req, in, finder)
    })
}
```

`search_workflows.go` mirrors this with `SearchWorkflowsName`, `"workflows://"`, helper `searchWorkflows`, and `RegisterSearchWorkflowsBootstrap`.

> **Note on missing `query`:** the SDK rejects calls with empty/missing `query` at the schema-validation layer (it sees `Query` is required via the `jsonschema` tag), so handlers never see invalid input — no manual validation needed in the handler.

## Implementation steps

### Step 1 — Extract a shared "walk + parse" helper

Currently `internal/server.go` walks assets and parses frontmatter inline. Move this into `internal/utils/assets.go` (or a new `internal/tools/helper.go`) so tools can use it without duplicating logic:

```go
// in internal/tools/helper.go (or internal/utils/)
func ListAllMetadata(finder utils.AssetsFinder) ([]ResourceMetadata, error)
func SearchMetadata(finder utils.AssetsFinder, query string, uriPrefix string) ([]ResourceMetadata, error)
```

`SearchMetadata` walks every asset, parses frontmatter, **and** searches the full body (the raw bytes read by `finder.GetAssetContents`). Case-insensitive `strings.Contains` against the lowercased query in: `URI`, `Name`, `Description`, and the document body.

**Refactor scope:** `internal/server.go`'s asset loop becomes a single call to `ListAllMetadata`. No behavior change for resources.

### Step 2 — Create `internal/tools/`

Files listed in the Architecture section. Each tool file is small (~30 lines): struct definitions + a handler that calls the helper.

### Step 3 — Update `internal/server.go` `BootstrapServer`

After the existing resource-registration loop, add a single generic loop over `tools.RegisterAll`. No per-tool code lives in `BootstrapServer`:

```go
for _, register := range tools.RegisterAll {
    register(server, finder)
}
```

Adding a new tool later = one new file in `internal/tools/` (with `Name`, `Description`, types, handler, and `Register<Name>Bootstrap` function) plus one new entry in `tools.RegisterAll`. **`BootstrapServer` never changes.**

### Step 4 — Tests

Add `internal/tools/tools_test.go` (unit tests for helper + handlers) **and** extend `internal/server_test.go` with end-to-end tests:


### Step 5 — Skill + rule

- `.agents/skills/mcp-tools-pattern/SKILL.md` — step-by-step "how to add a new tool" (use the existing `find-skills` skill format as the template). The skill emphasizes the per-file self-contained pattern: name, description, types, an **unexported** helper function, a `Register<Name>Bootstrap` function — plus appending to `tools.RegisterAll`.
- `.agents/rules/tool-conventions.md` — naming convention for tool names (`snake_case`, ≤128 chars, valid per SDK `validateToolName`), file layout in `internal/tools/`, what goes into the `Description` constant, that helpers must be **unexported** (lowercase) pure free functions taking dependencies as explicit parameters (no struct receivers), and that every tool file must export a `Register<Name>Bootstrap(server, finder)` function compatible with `tools.RegisterAll`.

Both follow the patterns of existing `.agents/skills/find-skills/SKILL.md` and `.agents/rules/resource-conventions.md`.

## Validation & testing strategy

- **Unit tests** for `ListAllMetadata` and `SearchMetadata` (happy path, no matches, body-only match, case-insensitivity).
- **End-to-end tests** via `mcp.NewInMemoryTransports` + `mcp.ClientSession.CallTool`, asserting on `result.StructuredContent` (typed struct, not raw JSON).
- **Schema validation tests** — pass invalid args (missing `query`, wrong type) and assert the SDK rejects them before the handler runs.
- **No-match tests** — empty result for queries that match nothing.
- **Make targets** — existing `make test` runs everything; no new target needed.

---

## Risks and open questions

1. **Body-search cost** — Re-reading every asset on every search is O(N). With the current corpus size (<50 assets) this is fine. If it grows, cache parsed content in memory at boot. **Decision: defer caching** until we have a real perf problem.
2. **Search across both frontmatter and body** — confirmed by the user that this is the desired behavior. Tools return metadata only; agent fetches full content via `resources/read`.
3. **Tool name validation** — SDK enforces ≤128 chars, alphanum + `_-.` only. Tool names like `discover_standards` comply.
4. **Schema drift** — SDK auto-infers JSON Schema from typed `Input` struct via `github.com/google/jsonschema-go`. If we add new fields, the schema updates automatically. No manual schema strings to maintain.
